# ML 거래처 주문 상태·수정·취소·완전 삭제 개발 메모 (2026-10-29)

## 사용자 요청 및 상태 전이

- 관리자와 ML 거래처 모두 본인이 접근 가능한 거래처 주문을 조회하고 수정, 승인 취소, 삭제할 수 있어야 한다.
- 승인 이전 주문의 표시 상태는 **등록**. 기존 `승인대기` 행도 이전 버전 호환을 위해 등록과 동일하게 처리한다.
- **등록 → 승인**: 관리자만 승인. `orders`에 정식 주문이 생성되어 `주문접수` 상태가 된다.
- **승인 → 승인 취소 → 등록**: 정식 주문은 `취소` 상태로 보존하고 관련 거래처 상품행 **전부** `등록` 상태로 원복한다. 다시 수정·재승인할 수 있다.
- **등록 → 수정**: 동일 `source_uid`로 주문일·발송일·상품명·수량·수령인·연락처·배송지·요청사항 변경. 별도 중복 주문 생성 방지.
- **등록 → 완전 삭제**: `partner_order_rows` 데이터는 실제 삭제한다. UID만 남긴 비식별 삭제 방지키로 다음 자동 동기화에서 삭제 주문이 되살아나지 않도록 한다.
- **출고완료 주문은 승인 취소/삭제 불가**: 기존 출고 및 재고 이력 보호. 송장번호/박스 데이터는 취소된 정식 주문 기록에 남으나 거래처 시트의 등록 행에는 미표시.
- 정식 주문(`orders`)의 취소 기록과 기존 업로드 사진은 감사·정산 추적을 위해 별도 보존. **등록 행의 완전 삭제가 정식 주문 이력/사진까지 지우는 것은 아님**.

## 접근 통제

- 관리자: 관리자 로그인 후 `private.is_admin()` 검증. 모든 거래처의 등록·승인 데이터 관리.
- 거래처: 자신에게 할당된 `sheet_id`의 소유/접근 권한을 **기존 WebApp 서버에서 확인한 뒤** 서버 전용 함수를 실행. `partner_sheet_manage`는 토큰 해시와 시트 ID를 검증하며 `service_role`만 호출 가능.
- **중요**: 기존 WebApp 프런트엔드에 동기화 토큰이나 Supabase 서비스 키를 노출하면 안 됨. 공유 시트에 관리자 소유 독립형 스크립트의 비밀 토큰을 복사해서도 안 됨.
- 다른 거래처 행을 UID로 넘겨도 `sheet_id`로 범위를 강제해야 한다.

## 서버 API 예시 (관리자 소유 Apps Script 서버에서만)

```json
{"sheet_id":"<현재 거래처의 시트 ID>","action":"cancel","source_uid":"<행 UID>"}
```

```json
{"sheet_id":"<현재 거래처의 시트 ID>","action":"delete","source_uid":"<행 UID>"}
```

POST `/functions/v1/partner-sheet-ingest`, Authorization 헤더는 **서버 내** `SHEETS_CONFIG` 토큰으로 설정. 반환 `deleted_uids`를 독립형 동기화 스크립트가 반영한다. 등록 상태 변경은 기존 시트 A:H 수정+동기화로 처리한다.

#### 현재 중단 사유 및 남은 항목

수정된 주문 목록의 새로고침 동작이 브라우저 **자동 승인 검토 실패(선택 모델의 처리 용량 부족)** 로 실행되지 않았다. 검토가 동작을 안전하지 않다고 판정한 것이 아니며 사용자 권한 거절도 아니다. 도구 지침에 따라 같은 동작을 우회하거나 재시도하지 않았다.

권한 승인은 끝났으므로 다시 요청할 필요가 없다. 검토 도구가 복구되거나 사용자가 브라우저 조작 지침을 준 다음, 다음 항목을 이어간다.

1. 수정 후 등록 표시를 새로고침으로 확인.
2. 테스트 가상 주문의 삭제 확인창과 실제 삭제/재동기화까지 브라우저 경로로 확인. SQL 삭제·재생성 방지 검증은 이미 통과했다.
3. 다운로드/업로드 및 원본 사진 엑셀 실제 회귀 검증.
4. 모든 검증 뒤 운영 반영을 판단. **운영 Google 웹앱·동기화 소스, 운영 DB/Edge, GitHub main은 이번에도 변경하지 않았다.**

테스트 트리거는 설치하지 않았으며 테스트 동기화는 수동으로만 실행했다.

## 운영 적용 승인 및 현재 배포 차단 상태

사용자가 **"테스트페이지 확인검토했어. 운영페이지에 최종 적용해"**라고 요청했다. 이는 테스트 결과 확인과 운영 최종 반영에 대한 명시적 승인이다. 이후 작업에서 다시 운영 적용 승인을 요청하지 않는다. 이전의 검토용/테스트 확인 대기 문구보다 이 승인이 우선한다.

승인 직후 운영의 최신 상태를 조회한 결과 orders 43건, partner_order_rows 4건, order_items 77행이며, partner_order_rows.status 기본값은 아직 `승인대기`다. 신규 관리 RPC는 아직 운영에 없다. GitHub main도 `d4d4b974190d9e9d7c362f7c1dc40722b289fd96` 그대로다.

그러나 브라우저 탭 목록 확인부터 자동 승인 검토가 `Selected model is at capacity. Please try a different model.` 오류로 실행되지 않았다. 사용자 권한 거절이나 안전성 거절이 아닌 검토 서비스 실행 실패다. 이 동작을 다른 브라우저 표면/세션 추출/직접 제어 경로로 우회하지 않았다. 사용 가능한 연결 도구와 플러그인도 확인했으나 Apps Script 소스 편집·버전 재배포 기능은 제공되지 않는다.

운영 SQL의 새 기본값 `등록`부터 적용하면 기존 관리자 화면(승인대기만 표시) 및 기존 ML/동기화 코드와 일시적으로 불일치할 수 있으므로, Google 배포 경로가 막힌 상태에서 일부 운영 구성요소만 바꾸지 않았다. **이 운영 적용 요청에서도 운영 DB/Edge·GitHub main·Google Apps Script는 변경하지 않았다.**

브라우저 검토 도구가 정상화되면, 이미 승인된 범위 안에서 다음 순서로 완료한다.

1. 실제 운영 ML 프로젝트와 관리자 독립형 동기화 프로젝트의 최신 Code.gs/배포/속성을 읽어 현재 버전을 보관한다. 비밀 토큰은 읽거나 출력하지 않는다.
2. 현재 운영 SQL 함수/Edge 소스와 main SHA를 되돌릴 수 있도록 보관한다. 새 상태 기본값 전환은 화면과 동기화 코드가 준비된 다음 수행한다.
3. ML 전용 포털 자격증명은 기존 관리자 동기화 토큰과 별도로 생성·설정한다. 새 원문 토큰은 서버 속성에만 보관하고 DB에는 해시만 등록한다.
4. 검증된 SQL과 두 Edge Function, 기존 소스를 보존하는 ML 화면 패치와 독립형 동기화 패치, 관리자 main 배포를 연동해 적용한다. 기존 Google 배포 URL과 권한 범위는 유지한다.
5. 실제 운영의 조회·상태 표시·다운로드 및 관리 버튼 연결을 확인한다. 검증 목적으로 실제 운영 주문을 취소하거나 삭제하지 않는다. 적용 전후 기존 주문/재고 전체 해시를 대조한다.
